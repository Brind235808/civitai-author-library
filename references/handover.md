# 交付：编号分册交接 + 图墙约定

## 为什么是这个结构

用户的会话常因上下文爆掉而中断。目标是**新会话只读 `00_INDEX.md` 就能决定下一步**，所以状态只落在两处（索引的状态卡 + 案例清单），其余分册写稳定事实；每份分册正文第一段必须是 ≤100 字纯总结。

## 文件布局

```
<库根>/
├── 00_INDEX.md              主入口：状态卡 + 编号目录 + 禁止预读清单
├── 01_方法与复跑.md          跨作者复用，换作者基本不改
├── 02_经验库结论_<作者>.md    每个作者一份，重写
├── 03_对比类型与案例清单.md    类型计数 + 可点名案例号
├── 04_数据与文件位置.md       目录树 + 字段定义 + 服务与排错
└── <作者>/                  数据全在作者目录下
```

编号固定、往后追加，**不重排旧号**；旧版单文档留档不删。派生类事实（待跑页号、坏文件清单）写成可复算的命令，不要手抄。

## 02 结论分册要写什么（省电费的部分）

按这个顺序，每条都标数据量（「从多少张里得出的」）：

1. **他收敛到哪几个底模**：Top N + 张数 + 首末使用时间 + 常配 LoRA。附「试过多少个 / Top5 占比 / 只用过一次的几个」——说明他是沉淀型还是猎新者。
2. **每个谱系的默认配方**：分辨率 / 步数 / CFG / 采样器 / clip_skip 的众数表。这是用户最可以直接抄的东西。
3. **LoRA 权重按用途**：把 LoRA 名分类（姿势动作 / 画风 / 细节增强 / 角色其他），给每类的四分位与中位权重。**注意这是「别人压出来的数」，本可省掉一整轮扫权重。**
4. **他靠什么控姿势**：姿势 LoRA 使用率、是否同时写姿势词、ControlNet 使用率（可能整库只有几张 → 说明这条路他试过就丢）。
5. **工作流变化**：按年统计管线开关使用率（Hires / ADetailer / 区域提示词 / clip_skip / 中位分辨率），而不是只看有没有换 ComfyUI。
6. **方法论 + 时代核对**（最重要也最容易漏）：他的单变量对照集中在哪个年代/谱系，用户的栈能不能直接吃。见 `comparison-kinds.md` 的分布表写法。
7. **已知偏差**：点赞不等于质量、缺失参数的老图、LoRA 名解析来源的局限。

## 图墙（`build_wall.py`）的约定

- 每个案例一张卡：标题 = 案例号 + 变化量 + 保持量；下面**并排**该案例的所有图。
- **被换掉的变量用红字**，保持相同的量用灰字列在旁边——用户第一眼要能确认「这组真的干净」。
- 每张图下面写全：底模 / LoRA+权重 / 采样器·步数·CFG·分辨率 / seed / 点赞，并给两个链接：`源数据`（本地 `meta/<id>.json`）与作者原帖。
- 顶部固定：作者画像表、谱系配方表、LoRA 权重表、试模广度，然后才是案例分区；分区顺序按 `comparison-kinds.md` 的优先度。
- 一个搜索框覆盖「底模名 / LoRA 名 / 姿势词 / 案例号」，用户报案例号就能定位。
- 图片一律 `loading="lazy"` + 绝对不要 `no-cache`；案例数或图片数上千时，缓存分档是必需的（否则每次滚动重打上千请求）。

## 服务：看门狗是交付的一部分

图墙依赖一个常驻静态服务，而「手动起、死了没人知道」就是最常见的裂图原因。所以：

- 用 `serve_guard.py <port> <库根>`，而不是裸跑 `serve.py`。
- 启动必须脱离会话：`powershell -NoProfile -Command "Start-Process -FilePath <python> -ArgumentList '<abs>\serve_guard.py','<port>','<abs 库根>' -WindowStyle Hidden"`。**nohup/后台作业方式起的进程会被会话回收带走。**
- 库不在服务根目录下时，用 junction（Windows `mklink /J`）/ 符号链接把库挂进服务根，URL 才通；这一步写进 04，下次能照做。
- 状态卡里必须写明：服务是什么、日志在哪、怎么确认活着（`netstat -ano | findstr <port>`）。
- 看门狗只防进程死，不防重启电脑；把「开机后要补一次启动命令」写进 04（要做成开机自启属于改系统设置，得先问用户）。
